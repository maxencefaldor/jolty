1. How a kernel's derivatives work today

Every kernel is a Rust function generic over a scalar type R: Real, and inside it uses Dual<R, N> for derivatives with respect to its voltages. Two things are differentiated, by two different mechanisms:

DerivativeMechanismWho uses it
∂F/∂x, for NewtonDual<R, N> slots seeded on the voltages a law reads (BSIM4's channel: vgs, vds, vbs), joined onto the terminals by the chain ruleEvery Newton iteration, with R = f64
∂F/∂p, for gradientsThe scalar type itself: R = Gradient (a value and its derivative with respect to one parameter), the parameter seeded when the device's parameters are lifted, prepared again and evaluated again. That instance is a twinSensitivity, mismatch, the JVP and VJP: one twin per (device, parameter)

Because the dual slots carry R, a twin's stamps also hold ∂J/∂p (each conductance's and capacitance's derivative), which AC and transient derivatives need. A self-heated device uses Hyper instead of Gradient: two first-order directions (its temperature, a parameter) and their mixed second derivative.

So composition at natural widths is already the norm. Two real items come out of the audit: VBIC (for speed) and the hand-written ports (for one way of writing a model).

3. Step 2: every parameter derivative of a device in one evaluation

The problem

A twin carries one parameter. A device with k named parameters needs k twins, each one a full prepare and evaluate, at every point a derivative needs (once at an operating point, once a step backward through a transient). Each twin recomputes the device's values, identical in all k, beside its one derivative. Training a circuit's transistor sizes (two per transistor), or a kit's mismatch (several random variables per device), pays that k times over.

The design

  1. One number type family: Gradient<const K: usize>, a value and its derivatives with respect to K parameters, implementing Real as Gradient does (its chain scales all K slots by the slope). Today's Gradient becomes Gradient<1>. Likewise Hyper<K> for heated devices: the temperature direction, K parameter directions, and K mixed terms. Kernels change not at all: they are already generic over R.
  2. A twin carries a chunk of parameters: a device and up to K of its named parameters, slot i seeded on parameter i. One prepare and one evaluate give every stamp's derivative with respect to all K. A device with more named parameters than the largest K gets several chunks.
  3. Chunk sizes: a small fixed set monomorphized, such as 1, 2, 4 and 8. Each chunk takes the smallest size that holds its parameters: a crossbar resistor's one weight takes 1, a transistor's width and length take 2. The largest size is a threshold like any other, set from measured break-even cost with the timing protocol before this lands, never picked.
  4. The VJP: pull_back dots each chunk twin's K derivative columns with the adjoint λ, giving K parameter cotangents per evaluation. Its interface does not change: only the twins it loops over do.
  5. The JVP needs no chunks at all: a tangent t on the parameters is one direction. Seed each parameter's slot with its component of t in a single Gradient<1> per device: one evaluation gives (∂F/∂p)·t for that device, whatever the number of its parameters. Today that sum comes from one twin per parameter.
  6. Newton is never touched: it evaluates with R = f64 and its own small dual widths. Twins are separate instances, built and evaluated only on a derivative path, so no Newton iteration ever carries a parameter slot.
  7. A transient's backward pass recomputes, never stores: the refactor's VJP needs each step's λkᵀ ∂Fk/∂p; a chunk twin evaluates at each recorded step as it is reached backward. The waveforms are kept anyway, so this costs no memory beyond the twins themselves.

4. Step 2b: AC's gradient independent of the number of parameters

The refactor left one analysis whose VJP still costs a step per parameter: AC. Its matrix G + jωC moves with a parameter directly, and through the operating point: (∂J/∂x)·(dx0/dp). That second term is a central difference per parameter today, because a kernel gives no second derivatives in x.

The term can be moved to the adjoint side exactly:

λᵀ (∂J/∂x · dx₀/dp) v = gᵀ dx₀/dp, g = ∂/∂x (λᵀ J(x) v) (one gradient in x) gᵀ dx₀/dp = −(J₀⁻ᵀ g)ᵀ ∂F₀/∂p (one more transposed DC solve)

g is assembled device by device. Each device's share is the gradient of one scalar, λᵀ Jdev(x) v, over its few local unknowns, so it needs second derivatives only at the device's own width. After that, one transposed solve at the operating point and the chunk twins' ∂F₀/∂p give the term for every parameter at once.

The cost: kernels must read their voltages as R rather than f64, so that a twin can seed a voltage direction. Local would carry an optional tangent of the unknowns, and every kernel's voltage reads would go through it. That is an interface change across every kernel. It is the one real price in this design, which is why it is a stage of its own, done only if AC gradients over many parameters matter.

6. The measurement, planned, not run

What would decide step 3 (a shared differentiation pass), if it is ever needed:

  1. BSIM4 at one card and bias, evaluated in a loop by jolty's kernel and by ngspice's BSIM4v5load, on machine B (machine A's clock distorts profiles), the load stated.
  2. The same loop for jolty with R = f64 and the dual slots removed (values only), which isolates what the derivatives cost from what the model itself costs.
  3. A profile of jolty's evaluation by function: the dual arithmetic, the branches, the temperature-dependent numbers, the stamping.

If the derivatives' share is small, step 3 is never needed, and the gap, if any, lies elsewhere.
