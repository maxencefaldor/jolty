# GPU: any circuit on any device

Status: ⏸️ later, not now (the owner, 15 November 2026).
The design below is the owner's and the lead's, kept for when it starts.

## Goal

Any circuit, one or many, simulated on a CPU or a GPU by changing the device alone, as JAX runs any program on any device:

```python
simulation = Simulation(circuit, device="cpu")  # today
simulation = Simulation(
    circuit, device="cuda:0"
)  # same code, same API, same results to rounding
```

Done fully or not at all: one circuit and batches alike, every analysis, every model.
A small circuit may run slower on a GPU than on a CPU, as a small array does in JAX; it runs, and gives the same results to rounding.

## Decided

- **One model source for every device:** no model written twice.
    Every model is Rust code implementing `Kernel`, written by hand or generated by jolty's Verilog-A compiler (`models.md` 12), which writes the same form a person does (the owner, 15 November).
    A GPU runs those same kernels, compiled for it; the kernel rules (pure, no allocation, no panic) are what GPU code requires.
- **Results agree across devices to rounding, not to the bit:** a GPU's `exp` and `log` round differently, and the owner accepts it; `AGENTS.md` says so since 15 November.
- **TPUs are out:** circuit simulation needs 64-bit floats, which TPUs lack.
    Only data-centre GPUs (A100, H100, MI300) run 64-bit floats at speed; consumer GPUs run them at 1/32 to 1/64 of their 32-bit rate, and Apple's GPUs have none.

## Design

**What stays one:** the circuit, its elaboration and its structure (the unknowns and the matrix's pattern) are the same on every device; only where the numbers live and which code runs on them differ.

**The layout differs by device:** a CPU wants one circuit's numbers together; a GPU wants the same number of many samples together, so neighbouring threads read neighbouring memory.
For one circuit on a GPU, neighbouring instances of one model take that place.

**The engine's numeric core behind a device interface:** evaluation, assembly, the sparse solve and the step control, each a device's operation; the CPU becomes the first device, today's code moved behind the interface.

**The hard parts, hardest first:**

1. **One model source on both devices:** the Rust kernels compiled for a GPU, whose Rust compilers are still young; the GPU work's first test is one existing kernel, the diode, compiled for a GPU.
1. **The sparse solve on a GPU:** each Newton iteration solves a sparse system, a transient thousands of times; a GPU pays a few microseconds of launch per kernel and is poor at the solve's irregular work, so large circuits and batches gain and small circuits lose.
    A GPU sparse solver is needed: jolty's own, or a vendor's (NVIDIA's cuDSS), which would be a dependency for the owner to approve.
1. **Adaptive control on a GPU:** a transient's step and Newton's iterations depend on the data.
    For one circuit, the control stays on the host or runs as one long-lived kernel; for a batch, each sample steps on its own inside one kernel, as Julia's DiffEqGPU does for ensembles of ODEs.

**Order:**

1. The Verilog-A compiler, writing `Kernel` code (`models.md` 12; resistor and diode on `main` at `5b0063b`, four CMC models compile whole pending QA).
1. The numeric core behind the device interface, the CPU its first device.
1. The GPU device: batches and single circuits, every analysis.

**A step that pays on CPUs now and shrinks the GPU's later:** batches laid out with samples side by side in the CPU's vector lanes (`speed.md` 15), the layout a GPU needs.

## Blocker

No machine with fast 64-bit GPUs.
The lab's are workstation GPUs, 64-bit at 1/64 of their 32-bit rate (machine A: an RTX 3090 and an RTX 6000 Ada; machine B: two RTX A6000; machine C: two RTX 6000 Ada), about 0.5 to 1.4 TFLOPS each, near machine A's CPU: enough to prove a GPU device correct, not to make it fast.
Speed needs an A100 or H100, the owner's or rented.
