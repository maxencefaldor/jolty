# GPU: any circuit on any device

Status: ⏸️ later, staged behind Waves 1 to 2 and `speed.md` 15 (owner decision, 15 November 2026; hardware update, 20 November 2026).
The design below reflects decisions by the owner and the lead, retained for when GPU work begins.

## Goal

Any circuit, single or batched, simulates on a CPU or a GPU by changing only the device parameter, as JAX runs any program on any device:

```python
simulation = Simulation(circuit, device="cpu")  # today
simulation = Simulation(
    circuit, device="cuda:0"
)  # same code, same API, same results to rounding
```

Done fully or not at all: single circuits and batches alike, every analysis, every model.
A small circuit may run slower on a GPU than on a CPU, as a small array does in JAX, yet the circuit still runs and matches to rounding.

## Decided

- **One model source for every device:** no model is written twice.
    Every model is Rust code implementing `Kernel`, written by hand or generated by jolty's Verilog-A compiler (`models.md` 12) in the same idiomatic form (the owner, 15 November).
    A GPU runs those same kernels compiled for the target device, because the kernel rules (pure, no allocation, no panic) match GPU execution requirements.
- **Results agree across devices to rounding, not to the bit:** GPU `exp` and `log` round differently, and `AGENTS.md` documents this owner-approved allowance since 15 November.
- **TPUs are out:** circuit simulation requires 64-bit floats, which TPUs lack.
    Only data-center GPUs (A100, H100, MI300) run 64-bit floats at full rate.
    Consumer GPUs run 64-bit floats at 1/32 to 1/64 of the 32-bit rate, and Apple GPUs lack 64-bit support.

## Design

**Shared representation:** the circuit, elaboration, and structure (unknowns and matrix sparsity pattern) stay identical across devices.
Only data storage location and execution kernels differ by device.

**Device-specific memory layout:** a CPU groups values for a single circuit contiguously, whereas a GPU groups the same value across many samples so neighboring threads access contiguous memory.
For a single circuit on a GPU, neighboring instances of the same model fill adjacent lanes instead.

**Numeric core behind a device interface:** evaluation, assembly, sparse solves, and step control become device operations.
The CPU serves as the first device backend by moving existing code behind that interface.

**The hard parts, hardest first:**

1. **One model source on both devices:** compiling Rust kernels for GPUs relies on immature GPU Rust toolchains.
    The first milestone compiles one existing kernel, the diode, for a GPU.
1. **The sparse solve on a GPU:** each Newton iteration solves a sparse linear system, and a transient analysis runs thousands of solves.
    GPUs incur several microseconds of kernel-launch overhead and handle irregular sparse work poorly, so large circuits and batches gain while small circuits lose.
    GPU execution requires a sparse solver, either a custom solver in jolty or a vendor library such as NVIDIA cuDSS pending owner approval.
1. **Adaptive control on a GPU:** transient step sizes and Newton iteration counts depend on runtime data.
    For a single circuit, control logic stays on the host or runs inside a persistent kernel.
    For a batch, each sample advances independently within a single kernel, similar to Julia DiffEqGPU for ODE ensembles.

**Order:**

1. The Verilog-A compiler emitting `Kernel` code (`models.md` 12; resistor and diode on `main` at `5b0063b`, four CMC models compiling whole pending `qaSpec` QA).
1. Waves 1 and 2 on CPU: PDK correctness and native kit completion (`models.md` 8, 11 to 15, 23, 23b, 24), cached PDK translation and agent latency (`speed.md` 8, 16, 22), and differentiable analog design (`agentic.md` 9, 11, 23).
1. CPU SIMD sample-lane structure-of-arrays layout (`speed.md` 15), delivering immediate AVX-512 batch throughput while validating the shared SoA layout GPUs require.
1. The numeric core moved behind the device interface, with the CPU as the first backend.
1. The GPU device backend targeting batched ensembles first (Monte Carlo, PVT corners, `jax.vmap`, and `trnoise` trajectories) on data-center H100s, followed by single-circuit solves and full analysis parity.

## Blocker

**Hardware blocker lifted (20 November 2026):** data-center H100 GPUs on internal Borg and XManager provide full-rate native 64-bit throughput (~34 TFLOPS vector FP64, ~67 TFLOPS FP64 Tensor Core), lifting the hardware blocker for batched GPU ensembles.
The lab workstations still carry workstation GPUs whose 64-bit throughput is 1/64 of the 32-bit rate, about 0.5 to 1.4 TFLOPS each, comparable to the machine A CPU (machine A has an RTX 3090 and an RTX 6000 Ada, machine B has two RTX A6000 cards, and machine C has two RTX 6000 Ada cards), sufficing only for correctness verification.
GPU implementation stays staged behind Waves 1 to 2 and `speed.md` 15 (CPU SIMD sample-lane SoA layout) so core PDK physics, differentiable analog design, and the shared SoA batch layout settle before GPU kernel work starts.
